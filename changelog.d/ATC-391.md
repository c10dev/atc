- K approval at release reaches landing: a `user`-tier PR built within the K3 effects the SUPERVISOR approved at release lands through MCC, with no second human step at merge (ATC-391, [docs/mcc.md](docs/mcc.md) L3, [docs/autonomy.md](docs/autonomy.md) "K approval reaches landing, as built").
  - MCC lands it only when its FLIGHT has a current release through the screen or the DUTY chat, the issue declares the K3 effect (`K3[<label>]: <control> | files: <paths>`) and every `user`-tier file in the diff is a declared file, INSPECTION passed on the head and CI passed. An attested release alone carries no K authority: the RELEASE screen lists it under "K 효과 확인" for one SUPERVISOR click (`POST /api/releases/k-confirm`).
  - Everything else stays with the SUPERVISOR with the reason shown: a change beyond the declaration, an ESCALATE, P0 or P1 findings, a PR that changes this check itself, migration and secret paths, a missing, stale or unreadable release or declaration.
  - On from the start; one off switch in the settings window (MCC, "K APPROVAL", `mcc.json` `kApproval`). Each landing records its release id on the `mcc.jsonl` `land` line, and the settings window counts such landings per day with the reverts and ROLLBACKs that followed.
