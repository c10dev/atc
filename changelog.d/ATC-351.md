### Added
- Auto-revert lane: when a merge MCC or AUTOLAND made turns `main` red, atc opens a revert PR of that merge, and the next green head clears the stop (ATC-351, [docs/autonomy.md](docs/autonomy.md) "C4 as built", [docs/mcc.md](docs/mcc.md), [docs/occ.md](docs/occ.md) 9.7).
  - One switch, `autoRevert` (`off` default, `shadow`, `on`), set only in the settings window (LANDING, "AUTO REVERT") through the `fromThisApp` route; no `atcctl` command. `shadow` writes `would-revert` lines (head, merge, failing check) to the new `auto-revert.jsonl` and nothing else.
  - Only merges recorded by MCC or AUTOLAND and confirmed on GitHub are reverted, newest first; a human merge, a PR touching migration (K1) or `user`-tier (K3) paths, a revert and a PR whose files cannot be read are never reverted: atc writes a `hold` line instead. One revert in flight per AIRPORT; the revert PR (GraphQL `revertPullRequest`, not a draft, no force-push) goes through the same review and CI, and is the one PR a main-broken GROUND STOP does not block.
  - A second new red head within an hour stops the lane: AUTOLAND `merge` drops to `update`, MCC landing goes off, one SUPERVISOR alert, and reverting stays stopped until the SUPERVISOR picks the switch again. DUTY (not the SUPERVISOR) gets the `AUTO-REVERT` lines in its brief; the reverted PR's FLIGHT gets a FIX relay naming the failing check.
  - Rules are pure (`server/auto-revert.ts`, tested), the cycle is `server/auto-revert-run.ts`. Settings and state are new files, so old state reads as `off`.
