# Research: ChatGPT accounts in atc (several Codex CLI logins, plan usage, Codex sessions)

**English** · [한국어](chatgpt-codex-accounts.ko.md)

> Status: SURVEY for [ATC-237](https://linear.app/vocado/issue/ATC-237/survey-chatgpt-accounts-in-atc-run-several-codex-cli-logins-one-codex), 2026-09-30. Docs only; no code, setting or `~/.codex*` / `~/.claude*` folder was changed, nobody logged in or out, no credential file (`auth.json`, `.credentials.json`) was opened or printed, and no model call was made on any ChatGPT account. Codex source facts are pinned to tag `rust-v0.154.0` (commit `6b9826e3`, the version installed on this machine) and cited with permalinks. Facts about other projects come from their public repos, fetched on 2026-09-30. Anything taken from an issue, a news page or a search summary is marked *unverified*. The local measurements used an empty scratch `CODEX_HOME` (never logged in) and field names of local rollout events only. ACCOUNTS appear by label only.

## 1. Question

The SUPERVISOR wants ChatGPT accounts next to the Claude ones: add several from the settings window, see them in the one ACCOUNTS list with their plan usage, and have AIRCRAFT fly Codex sessions on them ([accounts.md](../accounts.md)). Today ACCOUNTS is Claude only: `fleet.json` `accounts` = `{label: {configDir}}` and `checkConfigDir` accepts only folders whose name starts with `.claude`. For Codex, atc only reads one folder (`config.codexDir = ~/.codex`, `server/sources/codex.ts`: today's and yesterday's rollouts). It never launches or stops a Codex session, and FUEL does not read Codex `token_count` ([fuel.md](../fuel.md) 4, "Not in F1").

The issue's four questions: (1) several ChatGPT logins on one machine; (2) plan usage without a model call; (3) launching Codex sessions from atc; (4) what the terms say. Section 8 is the recommendation.

## 2. Method and what was measured here

- Public sources: the Codex source at the pinned tag, the Codex docs (`learn.chatgpt.com/docs`, the new home of `developers.openai.com/codex`), the public repos of the projects in section 5, OpenAI's published terms.
- `codex --help` and `codex <cmd> --help` (0.154.0). `doctor` says 0.159.2 is available, so the protocol below will drift.
- **Everything below that ran `codex` ran with `CODEX_HOME` set to an empty scratch folder** under the job's temp directory, so `~/.codex` was never the target. Commands: `codex login status`, `codex doctor --summary`, `codex app-server generate-json-schema --out <scratch>`, and a small script that starts `codex app-server` (stdio) and sends `initialize`, `account/read`, `account/rateLimits/read`, `account/usage/read`. None of them makes a model call; none can log in.
- **Local rollouts** (`~/.codex/sessions`, 445 files) were read as field names and counts only, never content.
- Not measured, and why: anything that needs a logged-in home. A logged-in `app-server` read would run against `~/.codex` (forbidden: it may refresh the token and writes state) or needs a login (forbidden). The implementation issue must measure it on an ACCOUNT the SUPERVISOR logs in (section 9).

### 2.2 Local rollouts: `rate_limits` depends on the model provider

From the field names of 445 local rollouts (no content read):

- `token_count` event payload keys: `info` (`last_token_usage`, `model_context_window`, `total_token_usage`) and `rate_limits` (`credits`, `individual_limit`, `limit_id`, `limit_name`, `plan_type`, `primary`, `rate_limit_reached_type`, `secondary`, `spend_control_reached`). `primary` and `secondary` carry `resets_at`, `used_percent`, `window_minutes`.
- `session_meta.model_provider` is `openai` in 431 rollouts, `opencodex` in 13, one other. Of 49,547 `token_count` events under `openai`, **40,239 (81 %) have a non-null `primary`**; under `opencodex` **0 of 373**. The newest `openai` rollout is from 2026-09-21; every later rollout on this machine is `opencodex`, and none of them has a non-null `primary`.
- Window lengths seen: 300 min paired with 10,080 min (a 5-hour and a weekly window), and single windows of 10,080 and 43,200 min. The data does not say which plan has which shape; FUEL must read windows by length, not by name.
- So the answer to "does the opencodex proxy matter for a second login": **yes for passive rollout reading, no for the app-server read.** The snapshot is produced only when the provider is OpenAI's own ChatGPT backend (`requires_openai_auth`, see 4.2). A folder whose `config.toml` sets `model_provider = "opencodex"` produces rollouts with null limits. A new ACCOUNT folder made by atc has no `config.toml`, so it uses the default provider, which is what FUEL needs. Copying this machine's `~/.codex/config.toml` into it would carry the proxy with it.

## 3. The Codex side (what lives in a `CODEX_HOME`, login, status, refresh)

Permalinks use commit `6b9826e3aa83b1a5947db50f4332cb9c65f1b340`. Short names below: `storage.rs` = `codex-rs/login/src/auth/storage.rs`, `manager.rs` = `codex-rs/login/src/auth/manager.rs`, `server.rs` = `codex-rs/login/src/server.rs`.

**3.1 One `CODEX_HOME` per account is the working method, not a documented feature.** `find_codex_home()` reads `CODEX_HOME` (must exist), else `~/.codex` ([home-dir/src/lib.rs](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/utils/home-dir/src/lib.rs)). Codex has no account profiles: issue [#4432](https://github.com/openai/codex/issues/4432) (`--auth-profile`, opened 2025-09-29) is still open with no maintainer commitment, its PR #4457 was closed unmerged, and several related requests (#43190, #44891, #9648) are open (*unverified*: read through the GitHub API, not from a maintainer statement). The official docs describe credential storage only ([auth](https://learn.chatgpt.com/docs/auth)).

**3.2 What lives in a home.** `auth.json` ([storage.rs L257](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/login/src/auth/storage.rs#L257)); `config.toml` and profile files `<name>.config.toml`; rollouts `sessions/YYYY/MM/DD/rollout-<ts>-<uuid>.jsonl` and `archived_sessions/` ([rollout/src/lib.rs](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/rollout/src/lib.rs)); `session_index.jsonl` (thread names, latest wins, [session_index.rs](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/rollout/src/session_index.rs#L21-L49)); `history.jsonl`; SQLite state (`state_5`, `logs_2`, `goals_1`, `memories_1`, `queue_1`, `thread_history_1`, [state/src/sqlite.rs](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/state/src/sqlite.rs)); `installation_id`; `memories/`; `skills/` and `skills/.system`; a global `AGENTS.md`; `app-server-control/` (the control socket) and `app-server-daemon/` (pid, lock, settings, [app-server-daemon/src/lib.rs L269-L293](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/app-server-daemon/src/lib.rs#L269-L293)).
- **Per account, never shared:** `auth.json` (or its keyring entry), `sessions/`, `archived_sessions/`, `session_index.jsonl`, `history.jsonl`, `memories/`, the SQLite files and `installation_id`. They hold one account's chats and usage. (That is the source-level reading; the docs do not say it.)
- **Safe to share:** `config.toml` and `<name>.config.toml` (except a `model_provider` you do not want everywhere, see 2.2), `AGENTS.md`, `skills/`.
- `CODEX_SQLITE_HOME` moves only the state databases ([state/src/lib.rs](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/state/src/lib.rs)); a sessions-only override was not found.

**3.3 Credential storage.** `cli_auth_credentials_store` is `file` (default, `CODEX_HOME/auth.json`), `keyring`, `auto` or `ephemeral` ([config/src/types.rs](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/config/src/types.rs)). The keyring entry is service `Codex Auth`, secret `CODEX_AUTH`, account `cli|` plus the first 16 hex characters of the SHA-256 of the canonical `CODEX_HOME` path ([storage.rs L163-L173](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/login/src/auth/storage.rs#L163-L173), read again during this survey), so two homes do not collide. On a headless Linux host there is usually no Secret Service, so `file` mode is the practical choice. `file` mode writes with `truncate(true)` and mode `0600`, **not** a temp file and rename, and takes no lock ([storage.rs L188-L204](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/login/src/auth/storage.rs#L188-L204), read again during this survey).

**3.4 Login without a TTY, from a web page.**

| Flow | Facts | Fit for the settings window |
|---|---|---|
| Browser (`codex login`, `account/login/start` type `chatgpt`) | A callback server on `127.0.0.1:1455` (fallback 1457), path `/auth/callback`. On `AddrInUse` the second login sends a cancel request to whatever listens on 1455, which stops the first login ([server.rs](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/login/src/server.rs#L880-L965); constants and the cancel read again during this survey) | **Poor.** The callback is `localhost` on the host, but the SUPERVISOR's browser is on the Mac, and two logins collide |
| Device code (`codex login --device-auth`, `account/login/start` type `chatgptDeviceCode`) | Prints a verification link (`…/codex/device`) and a one-time code "expires in 15 minutes"; hard timeout 15 min ([device_code_auth.rs](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/login/src/device_code_auth.rs)). Through `app-server` the answer is structured: `{type, loginId, userCode, verificationUrl}`, then a notification `account/login/completed {loginId, success, error}`; `account/login/cancel {loginId}` | **Good.** No port, works from any browser, no stdout scraping, completion comes as an event. Its stdout form was not run (starting it would contact the login service) |
| `--with-api-key`, `--with-access-token` (stdin) | A key or a workspace access token read from stdin ([cli/src/login.rs](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/cli/src/login.rs)); access tokens are documented for Business and Enterprise workspaces only ([access tokens](https://learn.chatgpt.com/docs/enterprise/access-tokens)) | Out of scope: atc would hold a secret |

**3.5 `codex login status`.** Prints to stderr and exits 0 when logged in by any method (`Logged in using ChatGPT`, `Logged in using an API key - <masked key>`, access-token variants), prints `Not logged in` and exits 1 otherwise ([cli/src/login.rs L469-L530](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/cli/src/login.rs#L469-L530); the logged-out output and exit code were also observed, 2.1). It prints no email and no plan. atc may keep `loggedIn` (the exit code) and a short `authMethod` (`chatgpt`, `apikey`, other); the masked API key text and anything else is dropped. The email and plan exist only in the app-server `account/read` answer (`Account::Chatgpt{email, planType}`, [v2/account.rs L32-L52](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/app-server-protocol/src/protocol/v2/account.rs#L32-L52)): atc must drop them before storing or showing anything (ACCOUNTS principle 3).

**3.6 Token refresh and two logins.**
- Codex refreshes the ChatGPT access token proactively when less than 5 minutes remain and again on an HTTP 401; the refresh endpoint is `auth.openai.com/oauth/token`; a new refresh token in the answer replaces the old one ([manager.rs](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/login/src/auth/manager.rs#L290), `persist_tokens`). The CI docs say stale tokens are refreshed "roughly every 8 days" ([ci-cd-auth](https://learn.chatgpt.com/docs/auth/ci-cd-auth)).
- **One home, two processes:** refresh is serialized inside one process by a semaphore; across processes there is **no file lock and the write is not atomic** (3.3). Codex reloads `auth.json` before refreshing and skips the refresh if another process already did (`reload_if_account_id_matches`, [manager.rs L2608](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/login/src/auth/manager.rs#L2608)), which narrows the race but is not a lock.
- **Two homes:** no shared global lock was found. Each home has its own `installation_id`, its own keyring key and its own daemon files. Two logins in two `CODEX_HOME`s can run sessions at the same time; what they must not share is the SQLite home (`CODEX_SQLITE_HOME`).
- **A copy of `auth.json`** keeps working only until its access token expires; if the original refreshed in the meantime and the server rotated the refresh token, the copy fails and needs a new login. Projects document this (section 5). It is why atc must not swap or copy credential files.

### 4.2 When `rate_limits` exist in rollouts

The snapshot is parsed from the model response headers (`x-codex-primary-used-percent` and the like, plus an SSE `codex.rate_limits` event; [codex-api/src/rate_limits.rs](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/codex-api/src/rate_limits.rs#L57-L102)) and used only when the auth is ChatGPT-managed and the provider is OpenAI's own with `requires_openai_auth` ([core/src/client.rs L1060-L1069](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/core/src/client.rs#L1060-L1069)). That matches the local data in 2.2. Source (a) therefore has the same blind spot as the Claude statusline: an ACCOUNT with no running session has no record.

## 5. Launching Codex sessions

| Mode | What it is | Session name / stop / resume | Where files land |
|---|---|---|---|
| `codex exec` (`-C`, `-s`, `--json`, `-o`, `--ephemeral`, `-p`) | One non-interactive run that ends when the turn ends ([exec/src/cli.rs](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/exec/src/cli.rs#L15-L80)) | identity is a thread id; `codex exec resume <UUID or thread name>`; **no stop command** (kill the process) | `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-<ts>-<uuid>.jsonl`; names in `session_index.jsonl` |
| `codex app-server` (`--listen stdio://`, `unix://`, `ws://`) | JSON-RPC server: `thread/start`, `thread/resume`, `thread/fork`, `turn/start`, `turn/steer`, `turn/interrupt`, `thread/name/set`, `thread/archive`, `account/*`, notifications `thread/*`, `turn/*` (schema generated here) | threads live inside the server process (and persist as rollouts); interrupt a turn with `turn/interrupt`; stop by ending the server | same rollouts |
| `codex app-server daemon` | A managed local app-server, **per `CODEX_HOME`** (`app-server-daemon/` holds pid, lock, settings); `bootstrap\|start\|restart\|stop\|version`. `codex agents` browses its sessions; `codex queue --thread <id or name> --message` adds a message to a running server | as above | as above |
| Interactive `codex` in a terminal multiplexer | What a person runs | none from outside | same rollouts |

There is nothing like Claude's `claude --bg` job table with `state.json`, `needs` and `suggestedReply`.

- **Session → ACCOUNT.** The rollout's folder says which home it is in (the rule for Claude). `session_meta` has no folder field. `readCodex` would need to scan every registered Codex home; today it reads one folder and only today's and yesterday's dates.
- **Hooks.** Codex 0.154 has lifecycle hooks declared in `config.toml` (`PreToolUse`, `PermissionRequest`, `PostToolUse`, `PreCompact`, `PostCompact`, `SessionStart`, `SessionEnd`, `SubagentStart`, `SubagentStop`, `UserPromptSubmit`, `Stop`, `Interrupt`; "prompt and agent hook handlers are parsed but skipped") and an older `notify` program called after each turn ([config reference](https://learn.chatgpt.com/docs/config-file/config-reference), [hooks/src](https://github.com/openai/codex/tree/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/hooks/src/events)). So the claim and health hooks have counterparts. There is **no statusline**: FUEL's per-session record (section 6 of fuel.md) has no Codex source; usage comes from 4.1 (a) or (b).
- **What an AIRCRAFT on Codex loses compared with Claude.** CREW subagents defined by the team (Codex has spawn edges and `SubagentStart` hooks, but a user-facing way to define custom subagents was not found at this tag); `CLAUDE.md` (Codex reads `AGENTS.md`, global then project root to cwd, 32 KiB limit, [agents_md.rs](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/core/src/agents_md.rs)); skills (a global `skills/` dir; a project-level path was not confirmed); `/clear` plus CREW BRIEFING flows; the job state file behind NEEDS YOU; Remote Control (Codex has its own `remote-control` for the app-server daemon, a different thing).

Patterns:
- Three ways to read plan usage appear: the undocumented HTTP endpoint with the access token (codex-auth, oc-codex-multi-auth, CodexBar's first path); the official app-server RPC (marivaldojr, codex-multi-auth, CodexBar's second path); rollout events (codex-auth `--skip-api`, atc's own FUEL for Claude transcripts). Only the last two need no token in the caller's hands.
- Three multi-account shapes: a `CODEX_HOME` per account (omarhoumz, CodexBar, marivaldojr's temp homes), one home with a swapped or symlinked `auth.json` (codex-auth, omarhoumz `use`), and in-process token pools with rotation (the OpenCode plugins, codex-multi-auth with a proxy).
- Every tool that copies or pools tokens has to cope with single-use refresh-token rotation. It is the dominant failure mode in their READMEs.
- Reading `auth.json` is universal; only ccusage avoids credentials.
- OpenAI has not shipped profiles (3.1). Issue [#41664](https://github.com/openai/codex/issues/41664) ("clarify whether multi-account proxies are supported") is open and unanswered (*unverified* beyond the API read).

## 8. How atc compares, and the recommendation

### 8.1 ACCOUNTS principles ([accounts.md](../accounts.md) 2) for Codex

| # | Principle | For Codex |
|---|---|---|
| 1 | One config folder per ACCOUNT, one daemon per folder | **Changes.** One `CODEX_HOME` per ACCOUNT carries over. "One daemon per folder" does not: a Codex session needs no daemon (`codex exec` is a plain process). An optional app-server (per home) exists. Reword as "one home per ACCOUNT, processes started with that home" |
| 2 | The registry holds a label and a folder, nothing else | Carries. Add a non-secret `provider` |
| 3 | Never read, copy or print credentials; status filtered to `loggedIn` and `authMethod` | Carries, with Codex specifics: atc never opens `auth.json` or the keyring entry (the Codex process does). `codex login status` gives the exit code and method only. `account/read` carries email and plan: drop them at the parser. The device `userCode` and `verificationUrl` are shown once on the page and never stored or logged, like the Claude login URL |
| 4 | Observed, not guessed | Carries: the ACCOUNT is the home a rollout is found in |
| 5 | The SUPERVISOR does account setup | Carries |
| 6 | A live FLIGHT never moves | Carries. **New:** ACCOUNT CHANGE only within one provider; a Codex ACCOUNT is not a target for a Claude AIRCRAFT |
| 7 | No token per session, no swapping the credential file | Carries and matters more: swapping `auth.json` is what most community tools do, and the source shows why it is unsafe (non-atomic write, no lock, rotating refresh tokens) |
| 8 | Not two-specific | Carries |

New rules this survey suggests: (R9) labels are unique across providers, since FUEL and FLEET PLAN key on the label; (R10) atc uses only Codex's own surfaces (app-server, rollouts, `login status`) and never an undocumented backend endpoint with a token; (R11) one login process per home at a time, and the device-code flow only; (R12) no memory sharing and no shared SQLite home between Codex ACCOUNTS (SHARE MEMORY does not apply); (R13) a new Codex home gets no `model_provider` override (2.2).

### 8.2 Recommendation

**Registry shape: one registry, a `provider` per entry.** `fleet.json` `accounts` entries become `{provider?: "claude" | "codex", configDir}`; no `provider` means `claude`, so old files read unchanged. For `codex` the `configDir` is the `CODEX_HOME`, and `checkConfigDir` accepts a folder name starting with `.codex` for that provider. The SUPERVISOR asked for one ACCOUNTS list, FUEL and FLEET PLAN already key on labels, and a second registry would duplicate label checks, the settings block and `maxLaunched`. Risk: every reader that loops over `accountFolders()` assumes Claude (sessions, `jobs/`, `projects/`, `claude agents`, `claude auth status`); the first step must make that loop provider-aware before any Codex entry exists, with tests that a Codex entry changes nothing for the Claude readers. The alternative, a separate `codexAccounts`, leaves the Claude path untouched but gives two lists, two label spaces and a second place to keep in step. Not recommended.

**ADD ACCOUNT / LOGIN / status for a Codex folder.**
- ADD ACCOUNT: label, provider `codex`, folder `~/.codex-<label>` (mode 0700). Write nothing else: no `auth.json`, no copied `config.toml` (R13). An optional "copy `AGENTS.md` and `skills/`" is safe but can wait. Register last, as for Claude.
- LOGIN from the settings window: atc starts `codex app-server` with `CODEX_HOME=<folder>` and `cleanEnv`, sends `initialize` and `account/login/start {type: "chatgptDeviceCode"}`, shows the returned `verificationUrl` and `userCode`, and waits for `account/login/completed` (or `account/login/cancel`). Stop the server after the notification or after 15 minutes (the code's lifetime). This replaces the Claude flow's URL scraping and code pasting with structured fields, and avoids the browser flow's port 1455. The stdout form `codex login --device-auth` is the fallback. Risk: the protocol is marked experimental and 0.154 is already behind (0.159 is out), so pin the fields used against `generate-json-schema` output in a test and treat unknown fields as ignorable.
- Status: `codex login status` per folder (exit code, then the method from the first line, `unknown` when it is not one of the known strings), cached like `claude auth status`. Keep only `loggedIn` and `authMethod`.
- No onboarding step equivalent to `.claude.json` was found; whether a first session in a fresh home asks anything (trust, model) was not measured (section 9).

**FUEL and plan usage.** Read usage with `account/rateLimits/read` from a short-lived `codex app-server` (`CODEX_HOME=<folder>`), on a slow cadence (for example 5 minutes, and on demand from the settings window), one account at a time. Map `primary` and `secondary` windows by `windowDurationMins` into FUEL's windows (seen: 300 and 10,080 minutes, and single 10,080 or 43,200 minute windows), and keep only `usedPercent`, `windowDurationMins`, `resetsAt`, `rateLimitReachedType` and `ordinaryUsageAllowed`: drop `planType`, `accountId` and credit balances. Use rollout `token_count` events as the passive source for running sessions and for token cost, as FUEL does for Claude transcripts; treat a null `rate_limits` as "unknown", never 0 %. An ACCOUNT with no record stays unknown, the same rule as [claude-usage-accounts.md](claude-usage-accounts.md). Do not call the undocumented `wham/usage` endpoint or read tokens (R10): the official read exists and needs no token in atc's hands. Risks: the app-server protocol is experimental; Codex may refresh the token while it runs, and a session in the same home may refresh at the same moment with no lock and a non-atomic write (3.3, 3.6), so keep the poll rare, never run two pollers per home, and show NOT LOGGED IN with a LOGIN button when `login status` later fails; also a home whose `config.toml` routes through a proxy still answers this read (it is provider independent), but its rollouts carry null limits.

**First LAUNCH scope for Codex sessions: build the smallest thing.**
- First: a **CODEX FLIGHT as one `codex exec --json` run** per FLIGHT, started by atc in a systemd scope (as `launchCommandOf` does) with `CODEX_HOME=<folder>`, `-C <STAND>`, `-s workspace-write`, the CREW BRIEFING as the prompt, the JSON event stream written to a file. Stop = end the scope. Resume after a limit or restart = `codex exec resume <thread id>`. The ACCOUNT is the home its rollout is in, so the observation rule holds. It needs no experimental protocol and no resident process per session.
- Needs with it: readers over every registered Codex home (`readCodex` today reads one folder and two dates); `claim` and `health` equivalents as Codex hooks in that home's `config.toml` (the `Stop`, `SessionStart` and `PostToolUse` events exist; `StopFailure`-style LIMIT detection was not checked); AGENTS.md pointers where the rules live in `CLAUDE.md`.
- Leave out for now: mid-turn steering and queued messages (`codex queue`, `turn/steer` need an app-server per session), NEEDS YOU for Codex (no job state file), ACCOUNT CHANGE to or from Codex, CREW subagents, SHARE MEMORY, and the `app-server daemon`. Add app-server threads later if steering is wanted.
- Risks: a run that ends when its turn ends is not an AIRCRAFT that waits for the next message, so a Codex AIRCRAFT is a FLIGHT-shaped worker at first, not a standing CAPTAIN; FLEET and DISPATCH assume standing sessions (they treat a finished background session as idle and re-LAUNCH it), so the first issue should define what "idle" means for a Codex AIRCRAFT before LAUNCH is built.

**Suggested order** (each one issue; tiers by the usual rules, registry and LAUNCH environment are `user`): (C1) `provider` in the registry and provider-aware reader loops, no Codex code path yet; (C2) readers for Codex homes (sessions, ACCOUNT by folder) and `login status` health; (C3) ADD ACCOUNT for Codex; (C4) LOGIN through app-server device code; (C5) FUEL: usage read and Codex `token_count`; (C6) LAUNCH `codex exec` flights; (C7) hooks; later, app-server threads.

## 10. Decisions for the SUPERVISOR

1. **Registry**: one registry with `provider` (recommended) or a separate `codexAccounts`.
2. **Usage source**: the official app-server read plus rollouts (recommended), with the undocumented endpoint excluded; or also allow the endpoint for ACCOUNTS with no running session (it needs atc to hold the token, against principle 3).

4. **First LAUNCH scope**: `codex exec` flights (recommended) or a resident app-server per session from the start.
