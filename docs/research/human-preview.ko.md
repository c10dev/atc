# 리서치: Human Preview 다시 보기(요약)

[English](human-preview.md) · **한국어**

> 상태: [ATC-39](https://linear.app/vocado/issue/ATC-39) 리서치의 공개 요약, 2026-09-28. **전체 보고서와 근거는 비공개 Linear 문서(ATC-39)에 있다.** 추천은 SUPERVISOR 결정이 필요하다. 이 문서는 애플리케이션 저장소의 게이트나 atc의 착륙 동작을 바꾸지 않는다.

## 질문

비공개 애플리케이션 저장소(Next.js, PR마다 Vercel Preview로 배포)에는 수동 **Human Preview** 게이트가 있다. 렌더된 UI를 바꾸는 PR마다 사람이 그 PR의 Preview를 열어 확인 목록을 해 보고, 결과(disposition)를 PR 본문에 적는다. 이 리서치는 두 가지를 물었다.

- 지금 방식을 편하게 만드는 것([ATC-37](https://linear.app/vocado/issue/ATC-37))이 아니라, 게이트 자체를 바꿔야 하나?
- 바꾼다면 어떻게?

## 방법

- **PR:** 2026-09-28 전 30일 동안 만든 PR을 모두 읽기 전용 `gh`(GraphQL)로 읽었다.
  - PR 본문과 **편집 이력**: 사람 확인이 필요하다고 표시된 시각과, 기록된 결과가 바뀐 시각을 알 수 있다.
  - ready-for-review 이벤트, 머지 시각, 리뷰 스레드.
- **다른 자료:** UI 결정이 어떻게 내려졌는지는 이슈 본문에서, 착륙 대기는 atc LOGBOOK에서 봤다.
- **분류:** 저장소에 이미 있는 시각 도구(headless 브라우저 검사, metrics·픽셀 회귀)를 정리하고, 사람이 확인하는 것을 "사람만 판단"과 "기계가 검사"로 나눴다.
- **한계:** 본문 편집은 모두 공용 소유자 계정이라, 작성자로는 사람과 에이전트의 편집을 가를 수 없다. 대화로 준 지적을 다음 push 전에 고쳤다면 흔적이 남지 않는다. 그래서 "기록된 발견 없음"은 기록이 없다는 뜻이지, 일어나지 않았다는 뜻이 아니다.

## 알게 된 것(일반화)

- **게이트의 비용은 기다림보다 글에 있다.** 게이트 절이 PR 템플릿의 대부분이고, UI PR 본문에서도 큰 몫을 차지한다. 사람 확인 PR 대부분은 다른 PR보다 오래 기다리지 않았다. 비용은 며칠씩 걸린 몇 건에 몰려 있다.
- **기록이 실제와 맞지 않는다.** 사람 확인이 필요하다고 표시된 PR 대부분이 결과가 대기(pending)로 적힌 채 머지됐다. 실제 결정은 사람의 머지였다.
- **기록된 발견이 없다.** 이 기간에 자동·에이전트 QA가 놓친 결함을 사람 확인이 잡았다는 기록은 없다.
- **사람이 정말 필요했던 것은 셋이다.**
  - 디자인 가운데 하나를 고르기
  - 실제 계정으로 로그인 흐름 확인(에이전트는 할 수 없다)
  - 실기기 느낌(터치, 모바일 Safari, 회전). 에이전트가 거듭 "확인 못 함"으로 적었다.
- **기계적인 쪽은 이미 대부분 갖춰져 있다.** 배치, 넘침, 대비, 회귀는 저장소에 도구가 있다. 다만 게이트가 아닐 뿐이다.

## 추천: 위험 기반 증거 묶음

- **모든 UI PR**에 기계가 만든 **증거 묶음**을 붙인다: 건드린 경로의 전후 스크린샷(세 폭, 라이트·다크), 움직임은 짧은 영상, 작업의 완료 기준에 대한 에이전트 visual QA 결과.
- **사람은 세 등급에서만 필요하다.**
  - **CHOICE**: 새 화면이나 시각 방향, 브랜드·문구 톤, 대안 가운데 고르기. 증거 묶음을 보고 승인한다.
  - **ACCOUNT**: 로그인, OAuth, 로그아웃, 실제 계정 데이터 흐름. 지금 head의 Preview를 열어 적힌 단계 1~3개를 해 본다.
  - **DEVICE**: 터치, 모바일 브라우저 크롬, safe area, 회전, 임베드 플레이어. 실기기로 본다.
- **나머지**는 검사와 에이전트 QA로 착륙하고, 머지 뒤 staging에서 짧게 본다. 필요하면 빠르게 되돌린다.
- **사람 확인은 head SHA에 묶인다.** 뒤에 UI를 바꾸는 커밋이 오면 다시 확인하고, main만 병합한 경우는 이어진다(ATC-31 규칙).

### 단계별 도입

| 단계 | 바뀌는 것 | 도구 |
|---|---|---|
| 0. 규칙 | 긴 게이트 절을 짧은 "UI change" 칸으로 바꾼다: 영향, 등급, 증거 링크, Preview와 단계(ACCOUNT·DEVICE만), 사람 확인 결과 | 없음 |
| 1. 증거 묶음 | 에이전트 QA가 전후 스크린샷을 PR에 올린다 | 저장소에 고정된 Playwright |
| 2. CI 회귀 | main 기준에 대한 결정적 metrics 회귀를 CI에서. 픽셀 diff는 로컬에 둔다 | CI만 |
| 3. 재기 | atc가 UI PR마다 등급, 사람이 봤는지, 대기, 발견, 7일 안 되돌림을 적는다. LOGBOOK `measured` 방식(ATC-32/33)을 그대로 쓴다 | atc |

유료 시각 리뷰 서비스와 Preview 자동 접근(share 토큰, 보호 우회)은 SUPERVISOR 결정이다. 추천에는 둘 다 필요 없다.

## ATC-37: 바꾼다

핵심은 남긴다: 사람을 기다리는 것을 한곳에서 보고, head에 묶인 결과를 한 번에 남긴다. 범위는 줄인다.

- 대기열에는 CHOICE·ACCOUNT·DEVICE PR만 둔다.
- 한 줄에는 증거 묶음, ACCOUNT·DEVICE면 Preview 링크를 보인다.
- 통과·실패는 PR 댓글 하나와 짧은 결과 한 줄로 남긴다.
- 착륙 막힘은 등급 있는 PR에만 건다.

새 칸을 읽으므로 0단계가 채택된 뒤에 만든다.

## SUPERVISOR 결정

1. 증거 묶음과 0단계 규칙을 채택할지, 게이트를 두고 ATC-37을 원안대로 만들지.
2. 등급 없는 UI PR에 머지 뒤 staging 확인과 빠른 되돌림을 받아들일지.
3. 유료 시각 리뷰 서비스나 Preview 자동 접근을 허용할지. 둘 다 필요 없다.
