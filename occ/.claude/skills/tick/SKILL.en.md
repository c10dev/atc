# One OCC pass (`/tick`)

[한국어](SKILL.md) · **English**

> English translation for readers. The skill that runs is the Korean [`SKILL.md`](SKILL.md); this file is not loaded.

**Description:** One OCC pass — check whether the manual changed, review assignment proposals that have no note yet against the FLIGHT body and add notes and CAUTION; in approval mode, send approved proposals as FLIGHT PLANs and approved CREW CHANGEs to their AIRCRAFT, and record READBACKs; write SCHEDULE drafts (CLASSIFY, PRIORITIZE, CLOSE, shadow operation) for FLIGHTs with no classification or priority, or whose PR was merged while the issue is still open. Run it with `/loop 10m /tick`.

Read a procedure file (`.claude/skills/tick/*.md`, "Procedure files" in `CLAUDE.md`) only when its step has work. If there is nothing to do, don't open it.

0. `node ../controller/atcctl.mjs manual check`. On `CHANGED`, reread `CLAUDE.md` and this file, run `node ../controller/atcctl.mjs manual ack`, then continue under the reread manual. Read again, at its step, any procedure file you read before.
1. First handle any replies from CAPTAINs since the last pass. For a PR, review or done report, Read `.claude/skills/tick/following.md` and check with `gh` as in "When a team reports or the SUPERVISOR asks". If the report starts with the fixed header `[TEAM_X → OCC] ARRIVED …`, record its fixed lines **the moment you read it, before the `gh` check and before any other step** (ATC-169: a session that stops before recording loses the report) with `node ../controller/atcctl.mjs dispatch report <D-xxxx|ATC-n> --pr <n> --tier <t> --tests <pass/total|n/a> --discretion <n> --blocked <none|the blocker>` (ATC-124, `CLAUDE.md`). A completion report in the older shape with no header ("D-xxxx (ATC-n) done: <PR>") is recorded, with exactly the values it states, only when it gives the PR number, tier, tests, discretion and blocked all; if any is missing, don't guess to fill it: record nothing and note "no fixed report" in the OCC LOG (don't ask the team, ATC-152). For a FLIGHT PLAN or RECALL reply, Read `flight-plan.md`; for a CREW CHANGE reply, `crew-change.md`. For FLIGHT PLAN replies: "READBACK D-xxxx", run `node ../controller/atcctl.mjs dispatch readback D-xxxx`; for a decline with a reason, `dispatch decline D-xxxx -- <reason>`. A RECALL reply "READBACK D-xxxx RECALL" is `dispatch recalled D-xxxx`. A report that a STAND-free FLIGHT (SURVEY, CHECK) is done is `dispatch arrived D-xxxx -- '<result link or one line>'`. If it was assigned directly, with no D-xxxx, use `dispatch arrived <FLIGHT> --aircraft <TEAM_X> -- '<result link or one line>'`. A CREW CHANGE reply "READBACK CC-xxxx" (or "… CREW CHANGE CC-xxxx COMPLETE" arriving without a READBACK) is `crew-change readback CC-xxxx`.
2. Run `node ../controller/atcctl.mjs dispatch brief` and check `mode`. If `arrivalCandidates` (ARRIVED candidates for STAND-free FLIGHTs) has any, open each one's `evidence.url`: for GitHub, read-only `gh pr view <N> --comments`; for a Linear comment, `dispatch flight <FLIGHT>`. If it is that team's finished work for that FLIGHT, run its `command` unchanged. If not, or if unsure, don't run it and report to the SUPERVISOR. A candidate is only a suggestion: a wrong confirmation releases the AIRCRAFT early. If `arrivalMissing` (FLIGHTs whose PR merged with no arrival report, ATC-169) has an entry with `due: true`, write that FLIGHT in the OCC LOG and tell the SUPERVISOR once (the receiving session missed it or the CAPTAIN did not send it). Send no message asking the CAPTAIN. `due: false` may still be on its way, so wait.
3. For each proposal in `open` without a `note`, and each proposal in `open` or `held` without a `briefing`, but only those with `settled: true` (SETTLED, ATC-117: open for at least `settleMin` minutes, default 10, or approved). Skip the ones with `settled: false`: they may change soon, so give them no note or BRIEFING; the brief's `unsettled` counts them. If the server is old and has no `settled` field, treat every one as settled:
   - Read the body and comments with `node ../controller/atcctl.mjs dispatch flight <FLIGHT key>`.
   - Following the review rules in CLAUDE.md, run `node ../controller/atcctl.mjs dispatch note <ID> [--caution] [--hold [<FLIGHT>]] -- <note: English, it rides in the FLIGHT PLAN to the team>`. A prerequisite written only in the body, or a wait for a human decision, gets a `--hold`, not just a note. If the body or comments say "사용자가 정한다", "사용자 지시를 기다린다", "user decides" or similar, put a `--hold` without a prerequisite, whatever the AIRCRAFT ("The user decides" wording in CLAUDE.md).
   - If it has no `briefing`, Read `.claude/skills/tick/briefing.md` and follow it: `node ../controller/atcctl.mjs dispatch briefing <ID> --what '<무슨 일>' --why '<왜 이 AIRCRAFT>' --risk '<걸리는 점>'`. Write plain Korean, one sentence per line, and don't repeat the numbers in `briefs.<ID>.facts`. If you set a HOLD, give its reason in 걸리는 점.
   - After approval the server takes no HOLD or BRIEFING and a CROSSCHECK mark is impossible. So for each approved ASSIGN in `inFlight` with no `note`, right before `dispatch release` in step 4, read the body with `dispatch flight <FLIGHT key>` and add only `node ../controller/atcctl.mjs dispatch note <ID> [--caution] -- <note: English, it rides in the FLIGHT PLAN to the team>` (whether or not it is SETTLED). If the body shows a prerequisite or a wait for a human decision, say so in the note, add `--caution` and record it in the OCC LOG. Never delay the send.
4. If `mode` is `approval`, and `inFlight` has approved or recalling ones or `overdue` has any, Read `.claude/skills/tick/flight-plan.md` and follow "Sending FLIGHT PLANs": approved in `inFlight` → `dispatch release` → SendMessage the printed `SEND:` line (header only; if the result is `success:false`, run `dispatch undelivered D-xxxx -- <message>` right away, don't send again in the same tick and don't write "sent"); recalling in `inFlight` → `dispatch recall-send` → SendMessage its `SEND:` line (header only); and handle `overdue`. Then run `node ../controller/atcctl.mjs crew-change brief`; if it has `approved` or `overdue`, Read `.claude/skills/tick/crew-change.md` and follow "Sending CREW CHANGEs": `approved` → `crew-change send <CC-xxxx>` → SendMessage the printed `SEND:` line (header only) to that AIRCRAFT; don't send `waiting` ones; for `overdue`, resend the same text once, then report to the SUPERVISOR if there's still nothing. Only the SUPERVISOR approves. In `shadow`, skip this step.
5. SCHEDULE drafts (S1, shadow operation):
   - Run `node ../controller/atcctl.mjs schedule brief`. If `candidates` (including `candidates.waypoint`) or `waypointGaps` has work, Read `.claude/skills/tick/schedule.md` and follow "SCHEDULE drafts". If not, report WAYPOINT slips and ROUTEs without WAYPOINTs below and go to step 6.
   - Look at `candidates` and `examples` (the SUPERVISOR's recent decisions and rejection reasons). Don't repeat a mistake a rejection reason names.
   - If there are CLASSIFY candidates, first Read `../docs/fleet.md` (4.1 FLIGHT TYPE, 4.2 WAKE, 4.3 TYPE RATING). Decide the FLIGHT TYPE in the order from "Before a CLASSIFY" in `schedule.md` (BUILD only when behavior users see changes), and cite the sections applied in the reason.
   - For up to 3 candidate FLIGHTs, read each with `dispatch flight <FLIGHT key>`. If it is in `candidates.classify`, run `schedule draft CLASSIFY <FLIGHT> [--type …] [--wake …] [--rating …] -- "<reason>"`. If it is in `candidates.prioritize` and the body or comments give grounds, `schedule draft PRIORITIZE <FLIGHT> --priority <1-4> -- "<reason>"`. With no grounds, skip PRIORITIZE.
   - If it is in `candidates.close`, check the PR in `close.<FLIGHT>` with read-only `gh pr view` as in "Before a CLOSE" in `schedule.md`, then `schedule draft CLOSE <FLIGHT> -- "<PR, merge time, Fixes or not>"`. If there is no `Fixes` and done criteria look unfinished, don't draft. It counts toward the 3-per-pass cap and the 5 open drafts.
   - On `LIMIT`, stop drafting for this pass. Nothing is written to Linear.
   - Open `NEW` drafts (AD HOC FLIGHTs from the CHARTER DESK) count toward the limit of 5 too. A CHARTER REQUEST is not a per-pass duty; when the SUPERVISOR asks in this session, Read `schedule.md` and handle it as in "CHARTER DESK".
   - WAYPOINT slips: if `slips` has warnings with `fresh: true`, write only those in the OCC LOG, one line each (`text`), report them to the SUPERVISOR, then run `node ../controller/atcctl.mjs schedule slip-ack`. Don't report again what was already reported (`fresh: false`). If `slips` is `null`, atc couldn't read the milestones; skip. Don't message teams, and don't write drafts because of a slip.
   - ROUTEs without WAYPOINTs: if `routesWithoutWaypoints` has ROUTEs with `fresh: true`, follow "ROUTEs without WAYPOINTs" in `schedule.md`: one line per ROUTE in the OCC LOG and to the SUPERVISOR, then `node ../controller/atcctl.mjs schedule route-ack`. Don't report again what was already reported. Skip if `null`. Never create milestones.
   - WAYPOINT: if `candidates.waypoint` has FLIGHTs, follow "Before a WAYPOINT" in `schedule.md`: read the FLIGHT body and draft `schedule draft WAYPOINT <FLIGHT> "<WAYPOINT>" -- "<reason>"` only when one WAYPOINT's exit criteria clearly cover the FLIGHT. **At most 2 per pass.** When unsure, skip and note it in the OCC LOG. They count toward the 5 open drafts.
   - TARGET and ROUTE: if `open` and `recent` have no `TARGET` or `ROUTE` draft from the last 24 hours, Read `schedule.md` (if not read yet) and follow "TARGET and ROUTE drafts": read `atcctl network`, and draft only when the evidence is clear, **at most 1 per pass**. These get shadow verdicts only; nobody writes FLEET.
   - WAYPOINT gap: following "WAYPOINT gap" in `schedule.md`, find exit criteria in `waypointGaps` that no issue covers and draft them with `schedule draft NEW --gap --project <ROUTE> --milestone <WAYPOINT> …`. **At most 2 per pass**, starting with the active WAYPOINT. Quote the criterion with `> ` in the body's `## 목표`. Skip criteria a person must decide, drafts refused because a similar FLIGHT exists, and `truncated` WAYPOINTs, and note them in the OCC LOG. These count toward the limit of 5 open drafts.
6. If `mode` in `schedule brief` is `approval` (S2) and `inProgress` has approved or released ones, follow "SCHEDULE release" in `.claude/skills/tick/schedule.md` (Read it if step 5 didn't): for each approved in `inProgress` (except CLOSE — it is never released), `schedule release <S-xxxx>` → for each CALL in the output, pass its JSON unchanged to that Linear tool. If linear-guard blocks it or Linear returns an error, don't retry; report to the SUPERVISOR. In `shadow`, skip this step.
7. Flight following: run `node ../controller/atcctl.mjs following`. If there are issues with `fresh: true`, Read `.claude/skills/tick/following.md` (what each code means and whom to report to), then put only those in the OCC LOG, one line each, and report those with `severity: "warn"` to the SUPERVISOR. Then run `node ../controller/atcctl.mjs following ack`. Don't report already-reported ones (`fresh: false`) again, and don't message teams.
8. Leave a line or two of OCC LOG. If nothing happened, "특이 사항 없음" ("nothing to report").

It makes no decisions (approve or reject). If send-guard blocks a send, don't retry; report to the SUPERVISOR.
