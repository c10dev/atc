# OCC procedure: Sending FLIGHT PLANs

[한국어](flight-plan.md) · **English**

> English translation for readers. The OCC session reads the Korean [`flight-plan.md`](flight-plan.md), which is the source of truth; this file is not loaded.

Procedure moved from [`CLAUDE.md`](../../../CLAUDE.en.md). Read it (2b) in `/tick` steps 1, 2 and 4, when a FLIGHT PLAN or RECALL reply came in, `inFlight` has approved or recalling ones, `overdue` has any, or `arrivalCandidates` or `arrivalMissing` has any. `CLAUDE.md` sets the role and what OCC doesn't do.

## Commands

| Command | What it does |
|---|---|
| `node ../controller/atcctl.mjs dispatch release <D-0003>` | (2b) Mark an approved proposal sent and print `SEND TO` and the FLIGHT PLAN text. If already sent, print the same text again (for a resend) |
| `node ../controller/atcctl.mjs dispatch readback <D-0003> [@a1b2c3]` | (2b) The CAPTAIN read back. `@a1b2c3` is the work-order hash the CAPTAIN quoted in its reply (ATC-555): pass it exactly as the reply has it, and pass none if the reply has none. Never copy the hash from the brief or the FLIGHT PLAN |
| `node ../controller/atcctl.mjs dispatch unable <D-0003> -- <reason>` | (2b) The CAPTAIN replied "UNABLE D-0003 — reason" (same as `dispatch decline`; closes it) |
| `node ../controller/atcctl.mjs dispatch standby <D-0003>` | (2b) The CAPTAIN replied "STANDBY D-0003" (stays sent; READBACK overdue counts again once, from the first STANDBY) |
| `node ../controller/atcctl.mjs dispatch await-supervisor <D-0003> -- <reason>` | (2b) The CAPTAIN is neither READING BACK nor refusing but waiting for its user (the SUPERVISOR) (stays sent; the reason goes into `awaitSupervisor`; raises an alert). A later `dispatch readback` clears it |
| `node ../controller/atcctl.mjs dispatch undelivered <D-0003> -- <reason>` | (2b) The SendMessage result was `success:false` (ATC-183). Returns the sent proposal to approved, so `dispatch release` runs again when the session is back. Not a SUPERVISOR verdict; raises one CAUTION alert. Only for a sent proposal |
| `node ../controller/atcctl.mjs dispatch recall-send <D-0003>` | (2b) `SEND TO` and the RECALL text for a proposal the SUPERVISOR asked to recall (`recalling`). A resend gets the same text |
| `node ../controller/atcctl.mjs dispatch recalled <D-0003>` | (2b) The CAPTAIN replied "READBACK D-0003 RECALL" |
| `node ../controller/atcctl.mjs dispatch arrived <D-0003> -- <result link or one line>` | (2b) The CAPTAIN reported a STAND-free FLIGHT (SURVEY, CHECK) done |
| `node ../controller/atcctl.mjs exception <D-0003> --kind unable\|question\|silence [-- '<the CAPTAIN's text as given>']` | (2b) Exception judge (ATC-558): one action for an UNABLE, a question or a second silence. See "Exception judge" below |

## Sending FLIGHT PLANs (2b, only when `mode` is approval)

| Situation (brief field) | What to do |
|---|---|
| An `approved` ASSIGN in `inFlight` | `dispatch release <ID>` → if it answers 409 `atc 서버가 이 FLIGHT PLAN을 보낸다 …` (SERVER SEND, ATC-562), see the server send row below. Otherwise SendMessage the `SEND:` line (only the header `[DISPATCH D-xxxx]`) to the `SEND TO` session. send-guard swaps in the stored text (the full text below `---` is for the log; don't retype it). One per CAPTAIN per pass |
| That ASSIGN's AIRCRAFT is in `fuel.coldCache` of `dispatch brief` (a HOLDING CAPTAIN whose cache has gone cold, ATC-56) | Send it as above anyway: it only warns and never blocks. Put its `text` in the OCC LOG. Don't send a separate message to warm the cache |
| The CAPTAIN replies "READBACK D-xxxx @xxxxxx" | `dispatch readback D-xxxx @xxxxxx` (the hash as written). A "READBACK D-xxxx" without a hash: `dispatch readback D-xxxx` (a FLIGHT PLAN sent before the hash is accepted as before) |
| `dispatch readback` returns 409 `READBACK D-xxxx refused — … quote the work-order hash @xxxxxx …` (ATC-555) | The CAPTAIN quoted no hash, or a different one. Don't record it. Don't fill the hash in yourself and retry, and don't resend the FLIGHT PLAN because of this. Put the quoted hash (or "none") and the reply line from the error in the OCC LOG. A different hash means the CAPTAIN holds a different work order: report it to the SUPERVISOR. The card stays sent, and the READBACK overdue reaches the SUPERVISOR |
| `dispatch accept`/`decline`/`standby`/`await-supervisor` returns 409 `… answer the latest call D-yyyy` (ATC-554) | The CAPTAIN answered an older FLIGHT PLAN for the same FLIGHT. Don't record it on the old id; if the answer is about the new plan, run the same command on D-yyyy, otherwise put it in the OCC LOG. Never resend because of this |
| The CAPTAIN's final report `[TEAM_X → OCC] ARRIVED ATC-n · PR #n` (ATC-124) | The command is `/tick` step 0 (the moment it is read, before any other step). The free summary is not recorded. If `blocked-report` appears, report it to the SUPERVISOR. After `dispatch report` for a FLIGHT with no PR whose card is still `accepted` (no STAND ever seen), run `dispatch arrived <D-xxxx> -- <link or one line>` (ATC-266; the server accepts it only for a STAND-free FLIGHT or one with a recorded report). A completion report in the old form without the header ("D-xxxx (ATC-n) done: <PR>") is recorded only when the message itself states the PR number, tier, tests, discretion and blocked, with exactly those values; if any is missing, don't guess: record nothing and write "no fixed report" in the OCC LOG (don't ask the team, ATC-152) |
| The CAPTAIN replies "STANDBY D-xxxx" | `dispatch standby D-xxxx`. Don't resend; wait. A second STANDBY is recorded too, but overdue counts from the first |
| The CAPTAIN replies with neither READBACK nor UNABLE but "waiting for my user's go" (e.g. user-tier files need the SUPERVISOR's confirmation) | `dispatch await-supervisor D-xxxx -- <reason as written>`. Don't resend, don't retry, and don't relay an approval (never tell anyone "the SUPERVISOR approved"). The atc alert and FOLLOWING report it to the SUPERVISOR. The one-line paste text in `confirm` is the SUPERVISOR's. If "READBACK D-xxxx" arrives later, run `dispatch readback D-xxxx` |
| The CAPTAIN reports a STAND-free FLIGHT (SURVEY, CHECK; DEPARTED at READBACK) done | `dispatch arrived D-xxxx -- '<result link or one line>'`. For one assigned directly without a D-xxxx: `dispatch arrived <FLIGHT> --aircraft <TEAM_X> -- '<result link or one line>'` |
| `recalling` in `inFlight` (the SUPERVISOR requested a RECALL in the tab or API) | `dispatch recall-send <ID>` → SendMessage the `SEND:` line (only `[DISPATCH D-xxxx] RECALL`) to the printed `SEND TO` session; send-guard swaps in the stored RECALL text. Only the SUPERVISOR requests a RECALL; OCC never creates one. Send it even during an enforced ground stop (recalling is the safe direction) |
| The CAPTAIN replies "READBACK D-xxxx RECALL" | `dispatch recalled D-xxxx`. The FLIGHT becomes a candidate again and is not proposed to the same AIRCRAFT for 24 hours. A "READBACK D-xxxx" without "RECALL" is a FLIGHT PLAN READBACK; don't mix them up |
| A recalling proposal in `overdue` (no READBACK for over 10 minutes after the RECALL) | Get the same text with `dispatch recall-send <ID>` and send it once more. If there's still nothing, report to the SUPERVISOR |
| The CAPTAIN replies "UNABLE D-xxxx — reason", or declines with a reason without the fixed form | First run `exception D-xxxx --kind unable -- '<the reason as given>'` and follow the "Exception judge" table below. On `EXCEPTION OFF`, `dispatch unable D-xxxx -- <the reason as given>`; don't resend; report to the SUPERVISOR (it also shows in FOLLOWING for a day). A RECALL has no UNABLE: it closes only with "READBACK D-xxxx RECALL" |
| Instead of a READBACK, UNABLE, STANDBY or waiting for the user's go, the CAPTAIN asks about the FLIGHT PLAN | Run `exception D-xxxx --kind question -- '<the text as given>'` and follow the "Exception judge" table below. On `EXCEPTION OFF`, report to the SUPERVISOR (OCC sends no answers to teams) |
| A sent proposal in `overdue` (no READBACK for over 10 minutes; from the first STANDBY if there is one) | Get the same text with `dispatch release <ID>` and send it once more. If there's still nothing (a second silence), act on the answer of `exception <ID> --kind silence`; on `EXCEPTION OFF`, report to the SUPERVISOR. If the card's `sentVia` is `server`, release answers 409: see the server send row below |
| An accepted proposal in `overdue` (no STAND for over 30 minutes after READBACK), or a STAND-free departed one (no ARRIVED report for over 24 hours) | Report to the SUPERVISOR only |
| **The SendMessage result is `success:false`** (sending a FLIGHT PLAN, ATC-183) | Run `dispatch undelivered D-xxxx -- <the tool's message, as returned>` right away. **Don't send again in the same tick.** Don't write "sent" in the OCC LOG; write "undelivered" and the reason. The proposal goes back to approved and comes up again next pass once the session is back. If the result is a success, add nothing (`dispatch readback` only after the READBACK arrives) |
| A RECALL was sent and the result is `success:false` | Don't send again in the same tick. Don't write "sent" in the OCC LOG; report to the SUPERVISOR. `recall-send` changes no state, so there is nothing to undo — the `overdue` (RECALL) rule of the next pass resends once |
| `dispatch release` refuses with `GROUND STOP — …` (an enforced ground stop covers that AIRPORT) | Don't send. Leave the approved proposal as it is until the stop is released. Put the stop's reason in the OCC LOG; for "main 깨짐" (main broken), check the failing check and commit with read-only `gh` and report to the SUPERVISOR |
| `dispatch release` refuses with `… LAUNCHING — 새 세션을 기다림 …` or `… RESTARTING …` (no session — waiting for the first message after /clear) (the SUPERVISOR approved a launch card and the session atc launched isn't up yet, ATC-129 and 91) | Don't send. The approval stays. Run `dispatch release` again next pass; once the new session is up it goes out as usual. Don't send anything to start or wake a session |
| `dispatch release` refuses with `AIRCRAFT 세션 없음 — 보내지 않음 (LAUNCH 필요)` (that AIRCRAFT has no live session and it is not a launch card, ATC-183) | Don't send. The approval stays. Note it in the OCC LOG and report to the SUPERVISOR (launching is the SUPERVISOR's call, from FLEET). When the session is back, run `dispatch release` again next pass. This refusal means no SendMessage was made, so `undelivered` is not needed |
| `dispatch release` refuses with `… LAUNCH 실패 …` (launch failed), or `following` has a `launch` issue | Don't send. Report to the SUPERVISOR (approving again or launching from FLEET is the SUPERVISOR's call) |
| `dispatch release` refuses with `FRESH START가 새 세션의 첫 프롬프트로 이미 보냄 …` (the SUPERVISOR sent that card with FRESH START: the FLIGHT PLAN was the new session's first prompt, ATC-73) | **Never send it again**, even for an `overdue` sent card: the same plan must not arrive twice. One line to the SUPERVISOR (no READBACK) is all. A card whose `sentVia` is `fresh-start` is not `release`d in the first place |
| **Server send** (ATC-562): `dispatch release` answers 409 `atc 서버가 이 FLIGHT PLAN을 보낸다 …` (an approved card) or `atc 서버가 보냄(sentVia server) …` (a sent card) | **Don't send.** While the switches are on, the server does the first send, one resend after 10 minutes without a READBACK, and one retry of an undelivered FLIGHT PLAN, through the same checks as send-guard. OCC handles only the replies (READBACK, UNABLE, STANDBY, waiting for the user's go) and the refusals and events: the CAPTAIN's reply still comes to OCC, so record it with the rows above. If the 409 says the server already resent once and the card is in `overdue`, that is a second silence: act on the answer of `exception <ID> --kind silence` (on `EXCEPTION OFF`, report to the SUPERVISOR). If it says resend is off, report to the SUPERVISOR. The 409 itself is not a SUPERVISOR report (one line in the OCC LOG). For a card the server failed to deliver twice, while the server job has been stopped for over 3 minutes, for desktop and terminal sessions, and while server send is suspended, release returns the text without a 409: send it as before. An undelivered FLIGHT PLAN arrives as a FOLLOWING `undelivered` issue (`following.en.md`) |

RELEASE proposals are not sent even when approved (the SUPERVISOR tidies them up in Linear).

## Exception judge (EXCEPTION JUDGE, ATC-558)

While the SUPERVISOR's switch (Settings → JUDGES → EXCEPTIONS, on by default) is on, OCC does not judge a CAPTAIN's UNABLE, question or second silence itself. `exception <D-xxxx> --kind unable|question|silence [-- '<the CAPTAIN's text as given>']` makes the server pick one action from a fixed menu (`RESEND` `HOLD_UNTIL` `REASSIGN` `ANSWER` `ESCALATE` `ACCEPT_UNDONE`) and answer with a first line `EXCEPTION EX-… · <action> · <source>` (Jev first; below confidence 0.8, one `claude -p` call). OCC only carries the action out, as the table says.

- If the output is `EXCEPTION OFF`, or the command ends in an error, do it the old way from the table above.
- Put the CAPTAIN's text inside single quotes as given (drop any single quotes inside it). The server masks paths, code and secrets, cuts it to 1,500 characters and sends that to the judge. Calling again with the same text does not judge again (`cached`).
- OCC cannot send text to teams (send-guard). So `ANSWER` never comes for a D- call: the ESCALATE card carries the proposed answer, and the SUPERVISOR sends it with RELAY.
- When the server sees a second silence first, it judges before waking you: on ESCALATE the card is already filed and you are not woken; for any other action the wake line carries `exception judge <action> (EX-…)`. Read the answer with `exception D-xxxx --kind silence` (no text) and carry it out.

| Action | UNABLE (`--kind unable`) | Question (`--kind question`) | Second silence (`--kind silence`) |
|---|---|---|---|
| `RESEND` | Do not record `dispatch unable`; get the same text with `dispatch release D-xxxx` and send it once more. On a server-send 409, don't send (the server resends once after `overdue`) | Same | Never comes |
| `HOLD_UNTIL` | `dispatch unable D-xxxx -- 'HOLD_UNTIL <WAIT FOR>: <the reason as given>'`. OCC LOG. No SUPERVISOR report. When a new proposal for the same FLIGHT appears, hold it with `--hold <WAIT FOR>` under the review rules | `dispatch standby D-xxxx`. `WAIT FOR` in the OCC LOG | `WAIT FOR` in the OCC LOG. No report |
| `REASSIGN` | `dispatch unable D-xxxx -- '<the reason as given>'`. OCC LOG. No report (the planner proposes another AIRCRAFT) | `dispatch unable D-xxxx -- 'REASSIGN: <the text as given>'`. OCC LOG | Never comes |
| `ACCEPT_UNDONE` | `dispatch unable D-xxxx -- '<the reason as given>'`. OCC LOG. No report | Never comes | Never comes |
| `ESCALATE` | `dispatch unable D-xxxx -- '<the reason as given>'`. With `CARD: DC-xxxx` the SUPERVISOR card is already filed: put only the card id in the OCC LOG, no separate report. With `CARD: not filed`, report to the SUPERVISOR | Record nothing; the card id in the OCC LOG (no card: report to the SUPERVISOR) | Same |

- The card's answer comes on a later tick as `decision-answered`. Act on it (what OCC cannot do, such as an answer to a team, the SUPERVISOR does with RELAY), then `decision ack occ <DC-xxxx>`.
- If the FLIGHT PLAN closes while its judge card is still open (a late READBACK, a RECALL, a CANCEL), withdraw it with `decision withdraw occ <DC-xxxx>` (the card has no PR, so it does not close by itself).
- Don't change a judgment or ask again about the same thing. The SUPERVISOR marks wrong judgments in Settings.
## Arrival candidates and missing arrival reports (`dispatch brief`)

- `arrivalCandidates` (ARRIVED candidates for STAND-free FLIGHTs): open each candidate's `evidence.url` (read-only `gh pr view <N> --comments` for GitHub, `dispatch flight <FLIGHT>` for a Linear comment). If it shows that team finished that FLIGHT's work, run its `command` as printed. If not, or if unsure, don't run it and report to the SUPERVISOR. A candidate is only a suggestion: a wrong confirmation frees the AIRCRAFT early.
- `arrivalMissing` (FLIGHTs whose PR merged with no arrival report, ATC-169): the OCC that received the report failed to record it, or the CAPTAIN did not send it (if this session stops before recording, the report is lost; the CAPTAIN does not send it again). If there is an entry with `due: true`, write that FLIGHT in the OCC LOG and tell the SUPERVISOR once. Don't send the CAPTAIN a question (there is no new send kind). `due: false` (merged under 30 minutes ago) may still be on its way. When you receive an arrival report, check this list to see whether it was already recorded.
